## 1. Definition of Workflow

| Колонка | Картка потрапляє сюди, коли | Картка виходить звідси, коли |
| --- | --- | --- |
| Backlog | Картка має унікальний F-ключ, тип `other`, результат, критерії перевірки й адресований артефакт ЛР5–ЛР6; для F-001 — посилання на §9 ЛР3. | Критерії конкретні, результат має обсяг на один-два дні, потрібні попередні артефакти доступні; картку обрано наступною. |
| Ready | Зафіксовано очікуваний результат і критерії; залежності позначені та не заважають цій роботі. Для інтеграційної історії окремо перевірено власника відповіді, факт запиту й тестовий приклад. | Є вільне місце в In progress, зафіксовано старт і розпочато роботу саме над результатом цієї картки. |
| In progress | Є фактична дата старту, вільний WIP-слот і виконавець — Войтюк Назарій; F-001 береться першою. | Результат існує у вказаному файлі або записі, усі acceptance checks доступні для перевірки й у Review є місце. Якщо місця немає, картка залишається тут. |
| Review | Є посилання на результат або локальний diff і checklist перевірки; картка займає слот Review. | Критерії перевірені, помилки усунені, зафіксовано докази та дату Done. Якщо перевірка не пройдена, повернення в In progress можливе лише за вільного слота. |
| Done | Усі критерії картки перевірені; результат збережено, а фактичний перехід і дата завершення записані. Це не означає приймання реальним замовником. | Якщо картку реально відкрито повторно, усі попередні переходи з Done залишаються в журналі, але поточне поле `Done date` очищається; первинне `Start date` зберігається. Після перевірки залежностей картка повертається в роботу за вільного WIP-слота, а остаточний Done отримує нову фактичну дату. |

Ці правила записані також у README живого Project; п'ять його статусів
відтворюють таблицю. Власна перевірка документів позначається як
самоперевірка, а не як
погодження викладачем або рольовим замовником. Definition of Done для історій
продукту з ЛР11 не підміняється цими правилами переходу.

## 2. WIP-ліміти

| Колонка | Ліміт | Чому саме такий |
| --- | :-: | --- |
| In progress | 3 | Стеля для одного виконавця: допускає вже розпочаті документальні кроки, але обмежує перемикання; це не ціль заповнити всі слоти. |
| Review | 2 | Не накопичувати неперевірені розділи статуту й беклогу; перед новою роботою завершувати перевірку результатів. |

Ліміти видимі в назвах реальних колонок: `In progress (WIP <= 3)` та
`Review (WIP <= 2)`. Це явна ручна політика, не автоматична заборона
переміщень і не твердження про встановлення native column limits.
Заголовки DoW вище — канонічні назви станів, суфікс показує їхній ліміт.

Що роблю, коли ліміт вичерпано: не починаю нову картку; перевіряю й завершую
вже розпочату або усуваю її перешкоду. Blocked-картка лишається у своєму
статусі й займає WIP-слот; приховування або перенесення в Backlog заради
звільнення слота не допускається. Очікування у Ready через WIP не є
зовнішнім блокуванням уже розпочатої роботи.

Коли ліміт спрацював: **pending — фактичної події ще не зафіксовано**.
Того ж дня потрібно записати F-ключ, дату, колонку, заповнення/ліміт і
конкретну дію замість запуску нової роботи; зараз таких даних немає.

## 7. Рішення ретроспективи з ЛР3

Рішення з [§9 журналу ЛР3](../lr03_sprint_simulation/sprint_log.md#9-ретроспектива):
перед Ready інтеграційної історії записати власника зовнішньої відповіді,
надіслати запит на доступ і отримати тестовий приклад даних. Без цих
підтверджень історія лишається blocked поза Sprint Backlog.

Практичний наслідок фіксується у **F-001**, першій картці в роботі.
Виконано перевірку для S-09; результат опубліковано також у README Project:

| Перевірка | Відомий стан | Що має стати доказом |
| --- | --- | --- |
| Власник зовнішньої відповіді | Не підтверджено | Роль відповідального за джерело розкладу та підтверджений канал відповіді |
| Запит на доступ відправлено | Факт відправлення не підтверджено | Дата та несекретне посилання/підтвердження запиту |
| Тестовий приклад отримано | Не підтверджено | Знеособлений приклад або посилання на доступний тестовий набір |

Контекст теми називає господарську й навчальну частини замовниками, але не
встановлює власника зовнішнього API. Їх не призначено вигаданими контактами.
Наступна зовнішня дія студента — уточнити відповідальну роль і канал,
надіслати запит та отримати приклад; цей документ не засвідчує їх виконання.
Поки що S-09 не може перейти в Ready або Sprint Backlog. Процесна F-001
завершилася перевіркою з негативним результатом; інтеграція від цього не
стала готовою. На момент F-001 `backlog.csv` був порожній; тепер S-09
заведена в продуктовий Project №2 як Backlog / Not Ready, не на F-дошку. Таке «не Ready» не
підміняє собою blocked days реальної, вже розпочатої історії.

Самоперевірка gate `owner AND request AND sample`: для трьох
непідтверджених входів результат **NOT READY**. Контрольні приклади з
відсутністю кожного входу та з усіма трьома входами пройшли 5 із 5
перевірок правила. Контрольні приклади синтетичні, а не дані про
отриманий доступ. Acceptance checks F-001 перевірено: невідомі позначені,
правило Ready зафіксоване, наступна зовнішня дія й доказ результату є;
саме після цього картка пройшла Review і Done. Ефективність gate на
майбутніх реальних історіях ще не доведена.

Шлях F-001 уже зафіксовано в §3: Backlog → Ready → In progress → Review →
Done того ж дня, першою в роботі. Що сталося за два тижні: **pending** —
дотримання gate на реальних інтеграційних історіях та двотижневий
підсумок ще не спостерігалися.
