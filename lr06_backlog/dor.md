# Definition of Ready

Войтюк Назарій (Hyptofon), КН-41; спільне бронювання, V07.
DoR — вхідний фільтр, не DoD і не факт приймання продукту.

## Умови взяття історії у спринт

Чотири умови «так/ні»; потрібні **всі чотири**:

1. У CSV є унікальний S-ключ, роль, дія, користувацька цінність та наявний SC-ключ для REL-1.
2. Є ≥2 окремі бінарні AC з очікуваним результатом; якщо можлива відмова чи невалідний ввід, описаний хоча б один негативний сценарій.
3. Для AC записані доступні вхідні приклади й правила перевірки. Синтетичні входи позначені; зовнішні дані не замінюються вигаданим доступом.
4. Залежності явно названі й завершені **або** впорядковані всередині того самого Sprint Backlog. Для зовнішньої залежності до Ready наявні **owner AND request AND sample**: підтверджений власник відповіді, доказ відправленого запиту, отриманий тестовий приклад. Без цього — Not Ready; F-001 доступів не створює.

Можна планувати S-11 після S-02, але не починати її до перевірки прав
S-02. Це не дозволяє брати S-04, що чекає історій поза поточним спринтом,
або обходити зовнішній gate.

## Чого DoR свідомо не вимагає

Не вимагаємо окремого підпису замовника для кожної історії чи макетів
кожного екрана: зайві черги для контрольного пілота. Не вимагаємо SP до
незалежної ЛР8; 2 історії — консервативний обсяг, не доведена місткість.
Після ЛР8 завелика історія потребуватиме розрізання й повторного Planning.

## Що робити з історією, яка не пройшла DoR

Історія лишається в Backlog із причиною Not Ready; BA дописує правила й
приклади, Dev перевіряє залежності, PM уточнює зовнішнього власника через
студента. Перевіряємо перед наступним Planning або після появи доказу.
Запити для S-01/S-09 студент ще має реально надіслати: документ не
засвідчує відправлення. Нерозпочатій історії не додаємо blocked days.

## Перевірка на власному беклозі

**2 з 10 REL-1 проходять DoR** для контрольного пілота. Перевірено під час
Planning; це готовність специфікації, не 2 завершені фічі чи 15 Ready-історій.

| Історія | Стан | Підстава |
| --- | --- | --- |
| S-02 | Ready | 3 AC; контрольні ролі й правила задані; зовнішній SSO не потрібний для локального тестового інкременту |
| S-11 | Ready, другою | 3 AC; каталог і негативні входи задані; S-02 у цьому самому спринті виконується першою |
| S-01, S-09 | Not Ready | Owner, request, sample не підтверджені |
| S-03 | Not Ready | Залежить від достовірних даних S-09 |
| S-04 | Not Ready | S-02/S-11/S-03/S-09; останні дві поза поточним Sprint Backlog |
| S-14, S-05 | Not Ready | Потрібна S-04 поза поточним спринтом |
| S-06 | Not Ready | S-02/S-04/S-14; останні дві поза поточним спринтом |
| S-07 | Not Ready | Потрібні S-04/S-06 поза поточним спринтом |

Доступні **синтетичні** входи, не акаунти/ресурси академії:

| Вхід | Очікуваний результат |
| --- | --- |
| T-applicant=applicant; T-approver=approver; T-admin=admin | Лише approver погоджує; лише admin змінює каталог; applicant працює зі своїми заявками |
| T-unknown: role=unknown або роль відсутня | Заборона за замовчуванням без зміни даних |
| R01: Аудиторія 1 / room / active=true / requires_approval=false | Адміністратор створює й читає запис |
| R02: Аудиторія 2 / room / active=true / requires_approval=true | Каталог зберігає вимогу погодження |
| E01: Проєктор / equipment / active=true | Збережено тип обладнання |
| Повторний ID R01; порожня назва; type=unknown | Кожний ввід окремо відхилено, попередній запис незмінний |
| T-applicant або T-approver змінює R01 | Відмова без зміни каталогу |

Це специфікація очікувань, не прогін реалізованих API: продуктовий код,
виконані тести й приймання S-02/S-11 ще pending. Матриця SC-04 з 18
перевірок на прийманні пілота ширша за ці мінімальні входи.
